# PRD 技术评审

## 工作流程

1. 读取用户指定的 PRD；没有明确文件时先定位当前项目中的 PRD，不凭摘要代替原文。
2. 读取 `.workspace/project-context.json`，确认已绑定的业务知识库、前端代码知识库和当前可写范围。
3. 按 `knowledge-search` Skill 检索 PRD 中的业务术语、页面、接口、字段、状态、权限、配置和埋点。
4. 只在必要范围内阅读代码，验证入口、调用关系、状态存储、接口封装和现有复用点。
5. 将结论分为：
   - 已证实：有 PRD、知识库或代码路径依据。
   - 风险：存在明确冲突、缺口或兼容性问题。
   - 待确认：现有材料无法判断，必须由产品、后端或业务补充。
6. 输出改动范围、关键链路、风险级别、待确认问题和可执行的评审建议。

## 输出结构

1. 评审结论：可进入开发 / 补充后进入 / 暂不建议进入。
2. 需求与现状对照：PRD 要求、当前实现、差异、证据路径。
3. 影响范围：页面、组件、状态、接口、数据、权限、配置、埋点、测试。
4. 风险与兼容性：按高、中、低排序，并说明触发条件。
5. 待确认项：问题、责任角色、阻塞范围。
6. 建议拆分：按可独立交付和验证的改动点拆分，不给未经团队校准的工时数字。

## 约束

- 不把文件存在当成实际调用证据；动态链路必须继续读取调用方或事件入口。
- 不补写 PRD 未定义的业务规则。
- 每个关键结论至少附一个具体文件路径；能定位行号时同时给出行号。
