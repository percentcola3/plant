# 脑暴流程通用骨架

> 本文件是 PM 与 UI 两个项目里 `pm-brainstorm` / `ui-brainstorm` 共用的骨架。
> 各 skill 通过 `§章节名` 引用本文件，差异部分（spec 落点、产物风格、术语口径）写在各自 SKILL.md。

## §HARD-GATE

任何创造性工作前必须先进入脑暴。**用户说"很简单 / 直接做 / 不用想了"——也必须先走完，无豁免。**

跳过本骨架直接 Edit / Write / 调用其它实施 skill = 违规。

例外：纯查询、纯解释、修单纯 typo、用户已有本脑暴产出的 spec 文档作为输入直接进实施环节。

## §9 步清单

进入 skill 后**用 TaskCreate 为每条建任务**，按顺序完成：

1. **探索项目上下文** — 见 §1
2. **判断是否需要图文设计** — 见 §2
3. **逐条澄清问题** — 一次只问一个
4. **提 2-3 个方案** — 各自取舍 + 推荐
5. **分节呈现设计** — 逐节确认
6. **写设计文档** — 落点见各 SKILL.md
7. **设计自检** — 占位符 / 矛盾 / 范围 / 歧义
8. **用户审 spec** — 等 ack
9. **语义化 git 收尾 + 移交实施** — 见 §9

**终态是移交，不是自己实施。**

## §1 探索项目上下文

硬动作（缺一不可）：

1. Read `.workspace/project-context.json`，记下 `activeWorkspace` / `activeRequirementId` / `editableRoots` / `kbRefs[].paths` / `uiAssets[].paths` / `externalRefs[]`。
2. Read `AGENTS.md` / `CLAUDE.md`，确认本工作区可写范围、知识库别名、项目规则。
3. 如 `kbRefs` 非空，用 `rg` 在 `kbRefs[].paths` 搜需求里的关键词、业务名、模块名、角色名。**知识库只读。**
4. 用 `rg` 在工作区内搜同类关键词，排除 `.external/**` `.claude/**` `.agents/**` `.cursor/**` `.workspace/**`。
5. 命中文档 Read 最相关 3-5 份；未命中明确说"知识库未命中"或"工作区未命中"。
6. `git log --oneline -10` 看近期改动节奏。

**范围预警**：需求横跨多个独立子系统（"做一个带聊天 + 文件 + 计费 + 分析的平台"），**立刻**指出来，先帮拆子项目，再脑暴第一个子项目。

## §2 视觉问题三档：ASCII 线框图 → 图文设计（mockup） → 纯文字版

涉及视觉判断时**先用最轻量的方式**，不够用再升级。判断顺序：

1. **ASCII 线框图（首选）** —— 直接在消息里画，不写文件、不开预览。
   适用：布局结构、模块划分、空间关系、信息层级、流程节点。绝大多数"位置 / 结构"
   类问题 ASCII 已经够清楚，不需要 mockup。

   ```
   ┌──────────────────────────────────────┐
   │ [logo]    [nav]    [user]            │
   ├──────────────────────────────────────┤
   │  hero ┌──────┐                       │
   │       │ CTA  │                       │
   │       └──────┘                       │
   └──────────────────────────────────────┘
   ```

2. **图文设计 / mockup HTML（次选）** —— ASCII 表达不了的细节才升级。
   适用：颜色对比、真实字号 / 间距比较、视觉冲击力、组件细节（按钮形态 / icon 风格 /
   阴影质感）。落 `ui/<topic>/.transient/q-<n>-<question>.html`，2-4 个
   `[data-uikit-choice]` 选项卡，用户在 App 右侧预览面板里点选。

3. **纯文字版** —— 跟视觉无关：需求范围、概念 A/B/C 选择、取舍清单、接口、数据建模。

**触发图文设计前先问自己**："ASCII 真的画不清吗？"——能画清就别开预览，少一次注意力切换。

启用图文设计时写 mockup HTML 到 `ui/<topic>/.transient/q-<n>-<question>.html`
（决策伴侣放 `.transient/`，不算 UI 产物），完整 HTML 协议 + 多选规则见各项目对应
SKILL.md 的"图文设计"段。

**怎么提示用户**：写完 mockup 之后说 "我已经把图文设计放到 `ui/<topic>/.transient/q-1-mode.html`，
请在右侧预览面板里点你想选的方案"——**不要**说"在浏览器里打开"，App 内置预览
能直接渲染并接收点击。聊天里出现的 HTML 路径会自动转成可点的预览按钮，
用户不用去找文件。

## §3 澄清问题

- **一次一个问题**。同一条消息塞多个 = 违规。
- 多选优先（A/B/C/D）。
- 焦点：目的 / 约束 / 成功标准。
- 听到模糊回答（"差不多"、"看你"）继续追问，别接着往下走。

## §4 提方案

**2-3 个**方案。每个带：
- 取舍（pro / con）
- 推荐选择
- 推荐理由

带头放推荐方案，把"为什么"说在前面。

## §5 分节呈现设计

每节按复杂度伸缩：直接 = 一两句；微妙 = 200-300 字。

每节末尾问"这部分对吗 / 有要改的吗"，等回复再走下一节。

**为隔离 + 清晰而设计**：拆职责单一、接口清晰、独立可测的小单元。每个单元能回答："它做什么 / 怎么用 / 依赖什么"。看不进内部能不能理解它做什么？改内部能不能不破坏调用方？不能则边界要重画。

**在已有代码里改**：先看现状再提改动。**沿用现有模式**。已有代码若有阻碍当前工作的真问题（文件过大、边界不清），把"针对性整改"作为本次设计的一部分提出来。**不提"顺手重构"。**

## §6 写设计文档

落点 + 模板由各项目 SKILL.md 给出（PM 偏需求 / 业务术语；UI 偏视觉 / 布局 / 组件结构）。

## §7 设计自检

写完别急着 ping 用户。**新眼光过一遍**：

1. **占位符扫描** — "TBD" / "TODO" / 模糊表述都修
2. **内部一致性** — 各节有没有自相矛盾？
3. **范围检查** — 本次实施够聚焦吗？
4. **歧义检查** — 任何一条要求能不能被两种理解？

inline 修，无需二次自检。

## §8 用户审 spec

发：

> "设计文档已写好并入库到 `<file>`，请审一下，有要改的告诉我；OK 的话我就调用下一个 skill 进入实施。"

等用户回复。要改 → 改完重走自检 → 再发上面这条。**OK 才能往下走。**

## §9 语义化 git 收尾 + 移交

App 的 auto-save saga 在每次文件变更后会 `wip(<branch>): <ISO>` commit + push。设计 spec 落地的 wip 应该重写成语义化 commit：

```bash
git log --oneline -10
git reset --soft <last-semantic-sha>
git commit -m "docs(<topic-slug>): 新增 <topic> 设计文档"
git push --force-with-lease
```

只在需求分支（`req/<id>-<slug>`）force-push。主干禁止。

**移交**：调对应实施 skill。具体名由各项目 SKILL.md 给出。**不要自己直接 Edit / Write 代码。**

## §10 图片还原模式

如果用户输入是**图片**（"参考这张图做"、"还原这个页面"），脑暴流程切到图片还原子模式：

1. **看图 + 描述** — Read 图片，输出三段：
   - 整体结构（页面分几屏 / 模块 / 主导航）
   - 关键元素（颜色、字体、组件类型、间距感觉）
   - 不确定的地方（"这块文字看不清"、"这个 icon 看着像 X"）
2. **画出 ASCII 线框** — 把理解画成线框图（用 `AskUserQuestion` 的 preview 字段或在 SKILL.md 末尾的"用户审 spec"步骤一并给出）
3. **用户确认** — 等用户回 "理解对" 或 "X 这块改成 Y"
4. **进入 §6 写设计文档** — 把图描述 + 用户修正一起写进 spec
5. **图片本身入工作区** — 让用户告诉路径或贴 base64；建议放 `ui/<topic>/source.<ext>` 保留作参考

**禁止**：直接看图就开始 build / 写 outputs。一定要先经过描述 + 用户确认。

## §关键原则

- **一次一个问题**
- **多选优先**
- **YAGNI 到底**
- **永远 2-3 方案**
- **逐步确认**
- **保持灵活** — 卡住就回上一步

## §触发后必做的第一条任务

进入 skill 后**第一件事**：

```
TaskCreate × 9，每条对应 §9 步清单
```

然后开始 §1 探索项目上下文。
