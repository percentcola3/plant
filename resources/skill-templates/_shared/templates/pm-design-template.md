# PM 设计稿模板（PRD 风格）

> `pm-brainstorm` 产出 `docs/<topic-slug>/design.md` 用这个骨架（日期写 §1 起源段，不进路径）。

```markdown
# <topic> 需求设计

> 日期：YYYY-MM-DD
> 起源：<触发本设计的需求 / 业务方 / 工单 / 数据洞察>

## 1. 背景与目标

<为什么做？解决什么用户问题？业务目标是什么？>

## 2. 用户与场景

- **目标用户**：<谁会用？画像？>
- **典型场景**：<什么时候 / 什么情境用？>
- **现状痛点**：<用户现在怎么解决这个问题？哪里不爽？>

## 3. 范围

**包含**：<列举功能 / 流程 / 页面>

**不包含**：<列举，注明排除理由——非常重要，避免 scope creep>

## 4. 方案

### 4.1 选定方案：<名称>

<功能 / 流程 / 关键交互节点 + Mermaid flowchart>

### 4.2 已考虑但未选

- 方案 B：<取舍 + 不选理由>
- 方案 C：<取舍 + 不选理由>

## 5. 关键规则与约束

| 规则 | 描述 | 来源 |
|---|---|---|
| R1 | ... | 业务方 / 法务 / 既有规范 |
| R2 | ... | ... |

## 6. 影响面（若涉及已有功能）

| 模块 | 影响类型 | 兼容性 |
|---|---|---|
| 登录页 | 改造 | 需要灰度 |
| 订单 API | 新增字段 | 向后兼容 |

## 7. 术语说明

| 术语 | 当前理解 | 是否已向用户确认 |
|---|---|---|
| PIX | 巴西本地支付 | ✓ |
| ... | ... | ✗ 待确认 |

## 8. 风险与兜底

<可预见的失败模式 + 业务兜底策略>

## 9. 验收

<功能验收清单——能让产品 / 测试 / 研发都达成共识>

## 10. 待确认 / TODO

- [ ] ...
```

## §写作风格（PM 项目特有）

- **短句优先**，少用复合长句
- **每段一个意思**
- **少黑话**："赋能 / 闭环 / 抓手 / 链路打通 / 能力沉淀 / 精细化运营"——必须用就补一句普通话
- **术语必登记**：业务术语 / 内部缩写 / 系统名 / 指标口径 / 角色名都列在 §7 术语说明
- **没确认的术语只能写"待确认"**，不能作为方案前提
