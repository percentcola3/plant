# 知识库检索

目标是先缩小范围，再读取少量高价值原文件。不要把整个资源包注入上下文，也不要把检索摘要当成事实。

当前会话的知识检索主路径是 MCP 工具 `mcp__zvec-grep__zvec_grep_search`（与 `zg_search` 相同）。不要说 MCP 不可用，也不要绕过它直接全目录 Grep。

## 1. 确定检索范围

1. 读取 `.workspace/project-context.json`。
2. 根据任务选择资源：
   - UX/UI：优先 `uiAssets`，再查前端代码知识库。
   - PRD/业务：优先 `knowledgeBase` 中的 Markdown、说明和业务目录。
   - 技术评审/代码复用：优先前端代码知识库，再用业务知识补充语义。
3. 尊重每个资源包的 `paths`、`visibleDirs`、`instructionPath` 和 `usageNote`；资源包只读。
4. 用户用 `@别名` 指定库时，`root` 用 `.external/<alias>`。

## 2. 先 zg 定位，再 Read 核实

对知识库、架构、调用链或未知措辞的问题：

1. 先调用 `mcp__zvec-grep__zvec_grep_search`，`root` 设为对应 `.external/<alias>` 或可读绝对路径。
2. 查询词要具体：完整业务短语、页面/组件名、接口/字段、`electron-builder`、`ia32`、`after-pack` 等。不要只用一次极宽的探测词（例如一串 `ia32/x64/DLL/架构`）就放弃。
3. 命中噪音时换更具体的词再搜 1-2 次，不要改去扫整库。
4. 把命中当作**候选路径**。结论必须 `Read` 原文件（必要时带 offset/limit 读命中附近），不要引用 zg 摘要当事实。
5. 每问挑选 3-5 个文件；需要实现证据时再沿 import、路由、事件、store 或 API 扩展 2-3 跳，最多 8 个证据文件。

## 3. Grep/Glob 只作补充

仅在以下情况使用 `Grep` / `Glob`（或 `rg`）：

- zg 换词后仍无可用路径。
- 已有文件，需要精确正则或符号名。
- 已知子树内补一行关键字（例如已定位到 `electron/`）。

不要用一次 zg 连通性探测代替检索，也不要在 zg 可用时把目录 Grep 当默认主路径。

## 4. 生成查询词

从用户问题提取最多 8 个词，包含：完整业务短语、页面或组件名、接口或字段名、状态值、常见中英文别名。过滤“怎么、如何、功能、实现”等低信息词。

## 5. 降级策略

- zg 未命中时，再用 `README.md`、`AI_USAGE.md`、`index.yml`、manifest 等仓库内说明路由，然后 Read。
- 仍无结果时才退回限定目录的 Grep；不要启动全库扫描。
- 精确词无结果时依次尝试别名、去掉前后缀、拆分复合词；仍无结果就明确报告未命中。
- 跳过 `.git/`、`node_modules/`、`dist/`、`build/`、`.zvec-grep/`、缓存目录、压缩包和二进制文件。

## 6. 返回结果

只返回与当前任务直接相关的内容：

- 结论或可复用对象。
- 资源包别名和具体文件路径。
- 命中的标题、组件、接口或字段。
- 事实依据与仍未确认的部分。

不要粘贴大段全文。没有证据时不要把推断写成事实。
